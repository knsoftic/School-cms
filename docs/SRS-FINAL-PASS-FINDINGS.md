**FR-SADMIN-007 (SRS-extracted.md:341, :343–344)**

The SRS makes the assignment the act that creates the link; the code requires the link to already exist, and the escape hatch its own comment names does not exist anywhere in the API. FR-SADMIN-007's preconditions are only "School record and Principal account exist" (:341), and its behaviour is "Super Admin selects a Principal for the school. / System links the Principal to the school, replacing any prior assignment when changing" (:343-344). `assignPrincipal` adds a third condition the SRS does not state — `Number(user.school_id) !== Number(school.id)` is refused with 422 "The selected Principal does not belong to this school" (schools.service.js:436-440) — which inverts the direction of the requirement: a Principal account that exists but belongs elsewhere cannot be selected, even though existence is the only stated precondition. The docblock justifies the refusal by deferring the move: "Moving a Principal between schools is a change to the *user*, and belongs to the user-management surface (SRS §33 \"Users\"), not to this endpoint" (schools.service.js:406-407). That surface refuses it outright: `users.validation.js:25-27` lists `organization_id` / `school_id` among the fields "deliberately not accepted" — "moving a user between tenants would make `users.school_id` disagree with the records that reference them … and there is no source requirement for a transfer" — and the `update` schema (users.validation.js:108-115) carries six fields, none of them `school_id`. There is no `POST /users` and no other writer of `users.school_id` outside `principals.service.create` (principals.service.js:231).
